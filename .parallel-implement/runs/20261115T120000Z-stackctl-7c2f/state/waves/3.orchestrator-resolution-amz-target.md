# Wave 3 — orchestrator resolution: X-Amz-Target signing seam

Escalation `w3-ssm-20261115T034643Z-ssm-x-amz-target-seam` (from `w3-ssm`,
`blocking: true`) reported that every SSM operation is AWS JSON-1.1 and needs a
signed `X-Amz-Target: AmazonSSM.<Operation>` header, which the frozen
`aws_req` / `sigv4_sign` surfaces could not express or sign. The lane cannot
work around it inside `core/ssm/**` without referencing network symbols.

Reply written: `inbox/w3-ssm/w3-ssm-20261115T034643Z-ssm-x-amz-target-seam.md.reply.md`
(`disposition: done`).

## Resolution — CONTRACT Amendment 5 (append-only, cites the escalation)

`CONTRACT.md` gains `## Amendment 5 — Signed extra request headers
(X-Amz-Target seam)` with `<!-- ref: w3-ssm-20261115T034643Z-ssm-x-amz-target-seam -->`.
It:

- adds `const char *const *extra_headers; size_t extra_header_count;` to
  `struct aws_req` (`core/aws/aws.h`), each entry a `"Name: value"` outbound
  line; `x-amz-*` names are signed, other names are sent but not signed except
  `content-type`;
- adds `sigv4_sign_with_headers(...)` to `core/crypto/crypto.h` (existing
  `sigv4_sign` unchanged), canonicalising names (lowercase/trim), values
  (trim/collapse spaces), sorting all signed headers, and rejecting invalid or
  duplicate names with `-EINVAL`;
- keeps `req.content_type` behavior as before and requires an empty extra set to
  reproduce the legacy signature byte-for-byte.
